# 音乐平台能力盘点与本项目补齐计划

> 目标是提炼主流产品的通用交互能力，形成原创的 Music Holo 体验；不复制竞品 Logo、专有文案、版权音频或商业素材。

## 市场能力观察

| 方向 | 成熟产品常见做法 | 对本项目的启发 |
| --- | --- | --- |
| 个性化发现 | Spotify 提供 Spotify Mixes、Discover Weekly、Release Radar、Daylist 等面向不同时间与偏好的歌单；Apple Music 根据聆听历史推荐艺人与专辑。 | 从收藏、最近播放、曲风分类、歌手偏好生成可解释的“为你推荐”，冷启动回落到热歌榜。 |
| 搜索 | YouTube Music 支持按歌词找歌；成熟搜索通常横跨歌曲、艺人、歌单等内容类型。 | 做统一搜索入口，歌词、歌名、专辑、歌手、歌单均可成为入口。 |
| 连续收听 | 个性化混音、自动续播、最近播放与年度回顾降低“下一首听什么”的成本。 | 保存每位用户的最近收听历史；支持续播、清空、删除单条，并以榜单补齐推荐。 |
| 社交与 UGC | Spotify 有好友分享、协作歌单与 Jam；网易云强调 UGC 歌单、乐评、一起听及社区。 | 当前已有用户歌单与收藏，下一阶段可补歌曲/歌单评论、关注歌手、分享链接、协同编辑与一起听。 |
| 歌词与演出 | Apple Music 强调实时歌词、翻译/发音；YouTube Music 用 Samples、艺人电台和视频帮助发现歌曲。 | 现有 LRC 同步播放已具基础；后续可加翻译歌词、多语言索引、相似歌曲电台。 |

## 与当前项目对照

### 已有

- 歌曲/歌手/歌单/分类浏览，关键字筛选与分页。
- 全息主题、收藏、个人播放队列、LRC 同步歌词、歌单 CRUD。
- 管理后台、文件上传下载、歌手 CSV 导入导出。
- 播放器适配窄屏，并支持空格播放/暂停、方向键跳转、Shift + 方向键切歌、L 打开歌词、Q 打开队列。

### 本轮补齐

1. **全站 3D 视觉贯穿**：统一空间环境层（透视网格、轨道光环、体积光与粒子），将景深玻璃、轻量卡片倾斜、播放器投影与动态主题覆盖到登录、内容、管理和播放流程，并尊重系统减少动态效果设置。
2. **统一搜索**：跨歌曲（标题/专辑/歌词/歌手）、歌手、公开歌单检索；搜索入口支持 `Ctrl/⌘ + K`。
3. **最近播放**：后端按用户保存歌曲与最后播放时间/次数，可分页、移除单项、清空；播放量接口对匿名访问开放，但只有登录用户写个人历史。
4. **个性化推荐**：按用户近期播放与收藏的歌手/分类做透明的内容匹配；新用户与匿名用户回落到热歌榜。这是可解释的冷启动基线，不宣称为机器学习算法。
5. **排行榜**：综合榜与分类榜，基于已有播放量排序。
6. **隐私补强**：私密歌单详情与曲目必须由创建者或管理员访问；匿名用户“只看我的”返回空结果。
7. **每日推荐入口**：新增独立的每日推荐页，复用用户近期收听/收藏画像，支持按曲风筛选、批量播放和加入队列；匿名访问回落到热歌推荐。
8. **睡眠定时**：播放器提供 15/30/45/60 分钟后暂停，或播完当前曲目后停止；切歌会取消“播完当前曲目”模式，跨路由保留。倒计时使用本机时钟，不是操作系统闹钟；刷新会重置，浏览器/系统挂起时可能延迟触发。
9. **公开歌单一键分享**：公开歌单详情增加原生系统分享与复制链接回退；私密歌单不显示分享入口，URL 由当前站点路由生成，不依赖第三方服务。
10. **本地音频与浮动播放器（本轮）**：队列支持多选本地音频文件，临时 Blob URL 只在浏览器内播放、不上传服务端，也不写入远程播放历史；固定播放器和歌词层 Teleport 到 body，脱离 3D / overflow 祖先布局，滚动页面时保持悬浮。刷新需重新导入；浏览器编解码支持因格式/平台而异。

## 下一步建议（按 ROI 排序，有明确收口条件）

> ROI 这里是“用户收益 / 实施与维护投入”的相对判断，不是未经测量的增长承诺。投入按熟悉当前 Vue + Spring 项目的一名全栈工程师估算，不含版权采购、内容运营和审核人力。当前没有真实用户行为基线，因此不写虚构的转化率提升百分比。

| 排名 | 建议 | 估算投入 | 完成后的可验证收益 | 验收条件 / 指标 | ROI 判断 |
| --- | --- | --- | --- | --- | --- |
| 1 | **真实浏览器主流程回归（本轮）**：在现有 Compose HTTP 冒烟测试之外，增加 Playwright 覆盖页面交互、路由、登录态和播放器。 | 首次搭建约 1–2 天；后续维护约 0.1–0.25 天 / 次变更 | 现有 CI 能验证容器、API、登录、收藏、历史、上传；浏览器测试再补“页面是否真的能点通”，减少 Mock/API 通过但真实 UI 失效的漏检。 | CI 用生产构建跑 5 条 Playwright 旅程：游客搜索/播放、demo 收藏/播放历史、公开歌单分享、本地音频导入与窄屏滚动固定栏、管理员仪表盘；失败时保留截图/trace/HTML 报告；不自动化每张表格。 | **高**：保护已完成能力，且能给后续社区功能提供回归底线；不直接带来用户增长。 |
| 2 | **歌曲 / 歌单短评 MVP（网易云社区方向）**：先做分页、发表/删除、点赞、举报与管理员隐藏，不做“一起听”。 | 约 3–5 天开发，另需持续审核时间 | 听众可补充歌曲/歌单语境和自己的发现；社区效果是否成立，需要观察真实发评与回访，不能预先承诺提升比例。 | 表结构迁移、权限隔离、长度/频率校验、举报与审核闭环；明确匿名可读/登录可发；试运行统计发评人数、举报量和单条处理耗时，再决定扩大。 | **中高（有前提）**：只有确定要经营社区并有人审核才值得做；没有举报/隐藏流程就不开放 UGC。 |
| 3 | **推荐反馈与最小测量**：记录推荐曝光、播放、跳过和“不感兴趣”，展示可解释原因，再据此调规则排序。 | 约 2–4 天开发；价值需等真实使用数据 | 能回答“推荐是否被点播、哪些内容被跳过”，让规则有证据可改；上线埋点本身不等于推荐已经变好。 | 先定义事件、隐私告知和删除策略；检查事件完整性后再比较曝光到播放、收藏等漏斗；样本不足时只报告计数，不宣称效果。 | **中**：缺少真实活跃用户时先不投入复杂算法；测量数据不足就暂停扩展。 |
| 4 | **关注歌手 / 协作歌单 / 一起听** | 约 1–3 周，另有长期运维 | 增加关系和共同收听场景，但会新增隐私权限、通知、同步冲突、反垃圾和在线状态问题。 | 先由访谈/试用确认需求；单独 RFC 定义权限、离线、举报和退出行为；任何一项未定义，不进入开发。 | **当前偏低**：维护成本远高于单个 Web 控件，等待歌单分享/短评的使用证据后再决定。 |

### 建议的版本收口线

- **本轮已收口**：Compose 整栈 / HTTP 冒烟与 Playwright 五条生产构建浏览器旅程通过 CI；覆盖游客搜索/播放、demo 收藏/播放历史、公开歌单分享、本地音频导入及窄屏滚动固定栏、管理员仪表盘。失败会留存截图、trace 与 HTML 报告。暂停无已知问题支撑的视觉微调。
- **下一小版本边界**：E2E 维持 5 条关键旅程，只在出现真实失败或行为变更时扩展；下一项产品功能候选是歌曲/歌单短评，但须先明确审核责任人和举报/隐藏流程，否则不开发 UGC。
- **只有明确要经营音乐社区时**，再立项短评/审核；没有审核责任人和投诉流程，不开放 UGC。版权曲库、MV、无损音源、实时一起听需授权或独立后端投入，不塞进 Web 微调。
- 达到上述收口线后，搜索、每日推荐、热榜、播放/队列、收藏、历史、歌词、歌单、分享、睡眠定时和管理后台可作为 **V1 可运行范围**；不宣称与网易云全功能等同。
- 每项通过明确验收后即停止该项；只有出现用户反馈、失败记录或实际使用数据，才开启下一轮改动。

## 权益与安全边界

- 版权曲库、MV、离线缓存和高解析音源需要授权与实际媒体服务，本项目不抓取第三方平台数据或素材。
- 现有音频为本项目生成的演示音频；生产环境应仅使用已获授权的文件，并配置版权、删除与投诉流程。
- 个性化历史与收藏均按用户隔离；提供删除/清空入口，不能通过猜测 ID 读取私密歌单。
